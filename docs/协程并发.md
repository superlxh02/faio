# 协程并发

并发接口把用户 `task` 包装成可以独立调度的根协程，并通过结果槽、完成事件或任务计数建立完成边界。本文解释任务如何启动、结果如何发布，以及父任务何时能够释放被子任务借用的状态。单个任务的帧协议见[协程封装](协程封装.md)。

## 1. 类与职责

| 类型或入口 | 源码 | 职责 |
| --- | --- | --- |
| `spawn` / `spawn_detached` | [faio.hpp](../include/faio/faio.hpp) | 立即提交任务，分别提供结果句柄或后台执行入口 |
| `join_handle<T>` | [join_handle.hpp](../include/faio/detail/coroutine/join_handle.hpp) | 独占结果消费权，支持协程等待、普通线程等待和停止请求 |
| `join_handle_state<T>` | [join_handle.hpp](../include/faio/detail/coroutine/join_handle.hpp) | 在根包装与句柄之间共享结果、异常和停止源 |
| `completion_event` | [coroutine_wait.hpp](../include/faio/detail/coroutine/coroutine_wait.hpp) | 带记忆的一次性协程完成事件 |
| `task_tracker` | [task_tracker.hpp](../include/faio/detail/coroutine/task_tracker.hpp) | 计数一组根任务，普通线程通过原子等待排空 |
| `detached_task` | [root_task.hpp](../include/faio/detail/coroutine/root_task.hpp) | 根协程包装；提交后在结束时自动销毁根帧 |
| `task_lifetime_ref` | [task_lifetime_ref.hpp](../include/faio/detail/coroutine/task_lifetime_ref.hpp) | 借用根任务生命周期服务，登记与归还活动根任务 |

| `join_slot<T>` / `join_child` | [combinators.hpp](../include/faio/detail/coroutine/combinators.hpp) | 保存每个并发分支的值或异常，完成时归还组合计数 |
| `select_state` / `select_child` | [combinators.hpp](../include/faio/detail/coroutine/combinators.hpp) | 仲裁胜出分支、发布结果、请求停止并排空候选 |
| `scope_state` / `scope_child` | [scope.hpp](../include/faio/detail/coroutine/scope.hpp) | 管理结构化任务组的计数、停止和首个异常 |
| `scope_context` / `scope` | [scope.hpp](../include/faio/detail/coroutine/scope.hpp) | 向 body 提供提交入口，并等待本组孩子退出 |

## 2. 启动与等待的关系

接口分为立即提交和惰性组合两类：

| 入口 | 启动时机 | 完成边界 |
| --- | --- | --- |
| `spawn(task)` | 调用时提交根包装 | 句柄的 `co_await` / `get()` 观察用户任务结果 |
| `spawn_detached(task)` | 调用时提交根包装 | 任务组或运行时的根任务计数覆盖其生命周期 |
| `join(task...)` / `join_all(vector)` | 返回的组合任务开始执行时提交分支 | 全部已提交分支退出结果写入路径 |
| `select(task...)` | 返回的组合任务开始执行时提交候选 | 胜出结果发布，并且全部已提交候选退出 |
| `scope(body)` | 返回的作用域任务开始执行时调用 body | body 结束，且本组孩子退出 |
| `block_on(task)` / `wait_all(ctx, tasks...)` | 普通线程调用时提交 | 对应 `task_tracker` 归零 |

worker 内调用无显式上下文的 `spawn`，使用当前调度器、任务组和停止令牌；普通线程调用时，经默认运行时服务提交。显式 `runtime_context` 重载将任务提交到指定运行时，并采用独立的根任务归属。

`spawn_detached` 的无观察者包装只等待并丢弃返回值。用户异常逃出该根包装时，根 promise 调用 `std::terminate()`。需要接收失败原因的任务，使用具有异常观察路径的入口。

## 3. 根协程提交与任务计数

独立提交的用户任务被包装在 `detached_task` 根协程中。根包装等待用户 `task`，并根据入口选择丢弃结果、写入结果槽或发布组合状态。

两种帧采用不同的结束协议：

| 帧 | 最终挂起 | 清理责任 |
| --- | --- | --- |
| 用户 `task<T>` | 保留帧并对称转移到父续体 | 父 awaiter 取结果后销毁 |
| `detached_task` 根包装 | `std::suspend_never` | 根协程结束时自动销毁 |

`start_detached()` 的流程是：绑定任务组清理目标 → 检查调度器 → 登记运行时根任务 → 绑定生命周期清理目标 → 交出根句柄 → 调度入队。入队失败时销毁根帧，由 promise 析构归还已经登记的计数。

根 promise 的析构处理两种计数：

```cpp
~promise_type() {
  if (scope) scope->done();
  if (lifetime) lifetime.finish_task();
}
```

`task_tracker` 表示一次调用的任务组，`task_lifetime_ref` 表示整个运行时的根任务生命周期。嵌套 `co_await` 的子帧由父 awaiter 管理；独立提交的根包装才参与根任务登记。调度引用负责执行安排，生命周期引用负责排空判断。

无观察者的根包装如果有异常逃出，会调用 `std::terminate()`。`join_handle`、组合器、`scope` 和 `block_on` 的根包装在协程体内捕获用户异常，将它交给各自的结果观察路径，详见后文各小节。

## 4. join_handle 的共享状态与结果消费

### 4.1 状态的所有权

`start_observed()` 构造 `join_handle_state<T>`，将一份 `shared_ptr` 交给根包装 `observed_coro()`，另一份交给返回的句柄。句柄移动转移消费权；根包装持有状态，使句柄先释放时任务仍能完成。

状态的核心成员如下：

```cpp
std::optional<handle_value<T>> value;
std::exception_ptr error;
completion_event completion;
std::atomic<bool> ready{false};
std::atomic<bool> consumed{false};
std::atomic<bool> abandoned{false};
std::stop_source stop_source;
std::optional<std::stop_callback<forward_stop>> parent_callback;
```

`handle_value<void>` 使用 `std::monostate` 表示成功。每个子任务有独立停止源；父停止令牌可取消时，在状态内登记回调，将父请求转发到子停止源。回调仅请求协作停止，不销毁任务帧。

### 4.2 根包装如何发布完成

`observed_coro()` 在等待用户任务之前安装任务组和子停止令牌。它捕获用户任务或结果构造的异常，写入 `value` / `error`，再执行 `publish()`：

```cpp
void publish() {
  ready.store(true, std::memory_order_release);
  ready.notify_all();
  completion.notify();
  if (abandoned.load(std::memory_order_acquire) && error)
    std::terminate();
}
```

`ready` 的 release/acquire 配对使普通线程看见已写入的结果；完成事件向协程等待者发布同一结果。句柄的完成表示用户结果已经可领取，根包装自身的析构则由运行时根任务计数跟踪。

### 4.3 普通线程与协程的等待路径

普通线程的 `wait()` 循环 acquire 读取 `ready`，未完成时调用 `ready.wait(false)`；`get()` 等待后调用 `take()`。在 worker 上阻塞等待会抛出逻辑错误，协程通过 `co_await handle` 等待完成事件。

左值和右值 `join_handle` 都可以等待，但都会把状态转移给 awaiter，原句柄随后为空。awaiter 持有状态并嵌入完成事件的等待节点，恢复后领取结果。

一次性消费由以下原子操作确定：

```cpp
if (consumed.exchange(true, std::memory_order_acq_rel))
  throw std::logic_error("JoinHandle 结果只能消费一次");
if (error) std::rethrow_exception(error);
if constexpr (!std::is_void_v<T>) return std::move(value.value());
```

重抛异常也算完成消费。`done()` 只查询完成状态；`request_stop()` 只请求停止；句柄析构不等待也不请求停止。未消费句柄被丢弃后，任务失败会触发终止规则：完成先发生时由放弃路径检查异常，放弃先发生时由发布路径检查异常。

## 5. completion_event 的登记与发布

完成事件用于结果句柄和并发组合的协程等待。内部原子指针有三种含义：

| 指针状态 | 含义 |
| --- | --- |
| `nullptr` | 未完成且没有等待者 |
| 等待节点链表 | 未完成，已有协程登记 |
| `&completed_` | 永久完成标记 |

等待者先 acquire 检查完成标记。未完成时，在 `await_suspend()` 中捕获句柄与调度器，以 CAS 将帧内节点头插到链表，再调用 `node.arm()` 完成登记交接。

通知的入口是：

```cpp
auto* nodes = waiters_.exchange(&completed_, std::memory_order_acq_rel);
if (nodes == &completed_) return;
```

一次交换同时发布结果、摘除等待链并关闭后续登记。通知方反转摘出的链表，按登记顺序投递恢复；后续等待直接完成，重复通知保持幂等。

登记与通知并发时，`wait_node` 的 phase 区分“登记中”和“允许异步恢复”。通知先到，则 `arm()` 失败，`await_suspend()` 返回 `false`；登记先完成，则通知通过保存的调度器重新入队。节点协议详见[协程同步](协程同步.md)。

完成事件不登记停止回调。并发组合在收到停止请求后，仍等待借用其状态的孩子退出，才能释放父帧。

## 6. block_on 与任务组计数

### 6.1 阻塞入口的源码流程

`runtime_context::block_on()` 的核心实现为：

```cpp
result_slot<T> slot;
task_tracker tracker;
tracker.add();
auto root = block_coro(std::move(child), &slot, &tracker);
start_detached(std::move(root), scheduler(), &tracker, task_lifetime());
tracker.wait();
return slot.get();
```

`slot` 和 `tracker` 存放在调用线程栈上。`block_coro()` 安装该 tracker，等待主任务，把值或异常写入 slot。根 promise 析构时调用 `tracker.done()`，主任务和组内派生根任务全部退出后，普通线程才能读取 slot 并离开栈帧。

`result_slot` 本身不带完成信号；它的可见性和生命周期由 tracker 的排空提供。tracker 使用原子计数：登记采用 relaxed 增加，完成采用 acq_rel 递减，最后一个完成者 `notify_all()`；普通线程 acquire 检查计数并执行 `atomic::wait()`。

### 6.2 派生任务怎样参与同一组

用户 `task` 的 context 保存 tracker，等待恢复时重新安装 `current_tracker`。使用当前执行上下文提交的 `spawn`、`spawn_detached` 及组合分支，在提交前增加该 tracker，并让根 promise 在析构时归还。

因此主任务的函数体结束，不等于 `block_on` 立即返回：已经登记到同组的独立根任务仍占有计数。嵌套 `co_await task` 由父帧等待链覆盖，不单独增加根任务计数。显式提交到指定运行时的入口使用其自己的提交归属。

`block_on` 和 `join_handle::wait()` 都拒绝在 worker 上阻塞，避免占用执行其依赖任务所需的线程。

### 6.3 wait_all 的分组方式

`wait_all(ctx, tasks...)` 为每个输入建立一个 `result_slot`，通过 `block_coro` 提交。提交阶段持有额外的 tracker 哨兵，全部提交尝试结束后归还哨兵，再等待计数归零，按输入位置收集 tuple。

中途提交失败时，也先等待已经提交的任务退出，再传播提交异常，保护栈上的结果槽。该入口要求输入任务具有非 `void` 结果；异构含 `void` 的协程组合由 `join` 的占位结果表达。

## 7. join 与 join_all：全部完成后收集

`join` 将异构结果槽保存在父组合帧的 tuple 中，`join_all` 为同类任务一次确定 vector 槽位数量。子根包装只借用对应槽位、计数和完成事件的地址。

计数从 1 开始，这一票是**启动哨兵**：

```cpp
std::atomic<std::size_t> remaining{1};
completion_event completion;
```

每个分支提交前增加计数。分支写入自己的值或异常后，执行：

```cpp
if (remaining->fetch_sub(1, std::memory_order_acq_rel) == 1)
  completion->notify();
```

启动阶段结束时，父组合器也归还一票。哨兵使快速完成的分支不能在其他分支仍待提交时提前发布整组完成。最后一次递减汇合分支写入，再由事件发布给父协程。

父任务无论正常提交还是中途失败，都先等待完成事件。完成后，提交异常优先传播；否则按输入位置取结果，遇到第一个失败槽位时重抛。结果顺序由参数或 vector 的位置决定，与完成先后无关；`void` 分支保留 `std::monostate` 占位。

分支沿用调用方的停止令牌，单个分支失败不会自动请求其他分支停止。空 `join` 返回空 tuple，空 `join_all` 返回空 vector。

## 8. select：仲裁、停止与排空

### 8.1 状态划分

`select_state` 在父组合帧中保存 `claimed`、胜出结果槽、`completion`、候选停止源、`running` 和 `all_done`。

这几个状态具有不同职责：

- `claimed` 仲裁唯一胜出权，不表示结果已经写好。
- `completion` 表示胜出值或异常已经发布。
- `running` 包含已提交候选和一个启动哨兵；归零时发布 `all_done`。
- `all_done` 表示分支结束状态访问，父帧可以释放被借用的存储。

### 8.2 分支如何获胜

每个候选先在自己的根帧内等待用户任务，并构造私有结果或异常。准备完成后，以 CAS 竞争胜出权：

```cpp
bool expected = false;
if (state->claimed.compare_exchange_strong(
        expected, true, std::memory_order_acq_rel)) {
  // 写入原参数下标，以及本分支的结果或异常
  // 结果移动异常也保存到 state->error
  state->completion.notify();
  state->stop.request_stop();
}
```

源码在发布事件前完成共享结果写入；值移动失败仍发布异常。失败分支同样可以获胜，父任务在排空后重抛胜出异常。落选分支丢弃私有结果，并在清理后归还候选计数。

候选提交起点由每个线程、每种模板实例的游标轮转。返回的 `index` 始终对应原始参数位置，`variant` 也按该下标存值，包括类型相同的不同候选。

### 8.3 父任务的返回条件

正常路径依次等待 `completion` 和 `all_done`，随后返回 `select_result{index, value}` 或重抛胜出异常。父停止请求转发到本次选择的停止源。启动失败路径等待已经提交的候选退出，再传播启动错误。

停止是协作请求；候选只有实际结束后才归还计数。因此胜出结果已经产生，父任务也可能仍在等待其他候选退出。这样的完成边界保证候选不会在 `select` 返回后继续借用父组合帧中的状态。

## 9. scope：结构化任务组

`scope(body)` 将 callable 按值保存到作用域协程帧，调用 `body(scope_context&)` 并保存其结果。`scope_state` 保存本组停止源、孩子计数、完成事件和首个异常；它同时借用调度器、外层 tracker 和运行时生命周期服务。

### 9.1 body 哨兵与孩子登记

本组 `remaining` 初始为 1，代表 body。`scope_context::spawn()` 立即提交孩子，并在提交前同时登记本组计数和外层 tracker。提交失败时，根帧归还外层计数，提交路径归还本组计数。

孩子包装等待用户任务，丢弃单个返回值，处理异常后调用 `state->done()`。body 结束时归还哨兵，作用域任务再等待完成事件；只有本组计数归零，才返回 body 的结果或异常。

只有 `scope_context::spawn()` 提交的孩子参与本组计数。在 body 中调用普通 `faio::spawn()`，采用的是该入口的任务组和结果句柄规则。

### 9.2 失败与停止传播

`scope_state::fail()` 在短互斥区内保存首次异常，释放锁后请求停止，避免停止回调在错误锁内执行。父停止令牌也通过回调连接到本组停止源。

| 结束原因 | 作用域处理 |
| --- | --- |
| body 正常结束 | 保存结果，等待孩子退出 |
| body 抛异常 | 记录首个异常，请求孩子停止，等待排空 |
| 孩子抛普通异常 | 记录首个异常，请求其他孩子停止 |
| 孩子抛 `operation_cancelled`，本组已请求停止 | 作为该次停止的退出路径，不新增异常 |
| 孩子抛 `operation_cancelled`，本组未请求停止 | 记录为本组失败并请求停止 |

排空后传播的是首先被 `fail()` 记录的异常，后续失败不会覆盖它。

### 9.3 借用对象的生命周期

孩子借用 `scope_state`，作用域协程等待完成事件，确保孩子不再访问该状态后才退出。`scope_context` 是操作视图，不拥有状态，其使用期限限于仍存活的作用域。

应用数据也需要有覆盖孩子执行期的所有者。例如，由包围 `co_await scope(...)` 的父协程帧保存共享数据。body 的局部变量随 body 结束销毁；作用域等待孩子不会延长这些局部变量的生命周期。

各机制的完成范围如下：

| 机制 | 完成范围 |
| --- | --- |
| `join_handle` | 一个用户任务的值或异常已发布 |
| `join` / `join_all` | 全部分支结果已写入，分支不再借用结果槽 |
| `select` | 胜出结果已发布，全部候选结束状态访问 |
| `scope` | body 结束，通过 context 提交的孩子结束状态访问 |
| `task_tracker` | 对应组内根包装完成析构 |
| 运行时根任务计数 | 该运行时全部登记根包装完成析构 |

运行时计数与这些局部完成机制共同保护调度器、线程和 I/O 资源的生命周期，详见[异步运行时](异步运行时.md)。
