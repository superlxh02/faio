# 协程封装

协程层负责保存任务结果、管理协程帧、传递执行上下文，并为所有异步等待提供统一的挂起与恢复设施。本文按源码文件解析 `include/faio/detail/coroutine/` 的整个封装层：任务帧协议、任务上下文、任务内查询与让出、等待节点设施，以及协程层与运行时之间的调度边界。根任务提交与并发组合见[协程并发](协程并发.md)，同步原语对等待节点的使用见[协程同步](协程同步.md)，调度器与队列的线程实现见[异步运行时](异步运行时.md)。

## 1. 文件与职责

## 2. task 的生命周期与帧所有权

调用返回 `task<T>` 的协程函数时，编译器构造协程帧和 promise，再通过 `get_return_object()` 生成任务对象。`initial_suspend()` 返回 `std::suspend_always`，所以函数体在创建任务时保持挂起。

```cpp
std::suspend_always initial_suspend() const noexcept { return {}; }

// task<T> 中的所有权转移入口
awaiter operator co_await() && noexcept {
  return awaiter{std::exchange(handle_, {})};
}
awaiter operator co_await() & = delete;
```

任务不可复制，只能移动。等待临时任务可以直接写 `co_await child()`；等待具名任务需要 `co_await std::move(child)`。转换完成后，原任务对象的句柄为空，子帧由 awaiter 独占持有。

帧的生命周期分为三段：

1. 创建后，由 `task<T>` 持有；未启动任务被销毁时，任务析构函数释放帧。
2. 等待后，由父协程中的 awaiter 持有；子任务运行或挂起期间，父帧和 awaiter 保持存活。
3. 子任务完成后，awaiter 领取结果或异常，再销毁子帧。

I/O 用户数据和同步等待节点可能借用帧内地址，因此挂起任务的结束依赖正常完成或协作取消。帧销毁本身不承担停止操作、摘除等待节点的职责。

## 3. promise、结果与对称转移

### 3.1 结果存储

共用 promise 保存三类状态：

```cpp
std::coroutine_handle<> continuation{};
std::exception_ptr exception{};
task_context context{};
```

`task_promise<T>` 使用 `std::optional<T>` 保存 `co_return` 的值。返回时原位构造结果，领取时先检查异常，再移动返回值。`task_promise<void>` 没有结果槽，领取完成状态时只检查异常。`task<T&>` 被静态断言拒绝；需要返回借用关系时，可以显式选择引用包装器等值类型。

`unhandled_exception()` 将异常保存在 promise 中，随后仍经过最终挂起。异常的传播位置是父 awaiter 的 `await_resume()`，因此父协程可以在 `co_await` 周围捕获子任务异常。

### 3.2 启动子任务

`task<T>::awaiter::await_suspend(parent)` 完成以下工作：

1. 将 `parent` 保存为子任务的 `continuation`。
2. 父 promise 有 `context` 时，复制父任务上下文；子任务显式设置的优先级在复制后重新应用。
3. 父 promise 没有 `context` 时，从当前线程的任务组和停止令牌启动子任务。这是根包装进入用户任务的路径。
4. 子任务尚无调度器时，从执行线程绑定取得调度器。
5. 安装子任务的停止令牌，返回子协程句柄。

最后一步返回句柄，形成父协程到子协程的**对称转移**。嵌套 `co_await task` 直接接续执行子任务，不为每一层调用分别向就绪队列提交一个根任务。

### 3.3 子任务结束与帧清理

最终挂起的核心实现如下：

```cpp
template <class Promise>
std::coroutine_handle<> await_suspend(
    std::coroutine_handle<Promise> child) const noexcept {
  auto parent = child.promise().continuation;
  return parent ? parent : std::noop_coroutine();
}
```

子任务结束时仍保留帧和结果，但将执行权交回父续体。父 awaiter 的结果领取使用局部守卫：

```cpp
T await_resume() {
  if (!callee) throw std::logic_error("co_await 空 task");
  struct frame_guard {
    handle_type handle;
    ~frame_guard() { handle.destroy(); }
  } guard{std::exchange(callee, {})};

  if constexpr (std::is_void_v<T>)
    guard.handle.promise().take_result();
  else
    return guard.handle.promise().take_result();
}
```

销毁责任先从 awaiter 移入守卫。正常返回、异常重抛以及返回值移动抛异常，都经过同一条帧清理路径；awaiter 随后的析构不会再次释放子帧。

## 4. 任务上下文与恢复适配

### 4.1 随帧保存的属性

`task_context` 的成员表示任务自身的执行属性：

| 成员 | 含义 |
| --- | --- |
| `scope` | 借用当前任务组的 `task_tracker`；派生根任务沿此归属计数 |
| `scheduler` | 所属调度域的借用引用；决定重新入队的目标 |
| `stop_token` | 当前任务观察的协作停止令牌 |
| `priority` / `priority_explicit` | 优先级元数据，以及是否由任务显式指定 |
| `budget` | `yield_if_needed()` 的协作预算，初始值为 64 |

`with_priority()` 在尚未交出的任务帧中记录显式优先级；嵌套任务继承上下文时保留这一设置。优先级值作为任务属性供查询，具体的入队与执行顺序由[异步运行时](异步运行时.md)的调度决定。

### 4.2 为什么恢复时需要上下文

线程局部的 `current_tracker` 和 `current_stop_token` 表示该线程此刻正在执行哪个任务。协程挂起期间，worker 会运行其他任务；协程再次恢复时，也可能位于另一个 worker。任务自己的 `context` 保存在稳定的协程帧中，恢复时由它重建线程局部状态。

共用 promise 的泛型 `await_transform()` 将等待表达式转换为底层 awaiter，再用 `scoped_awaiter` 包装。成员 `operator co_await`、ADL 非成员转换和 awaiter 本体都通过 `as_awaiter()` 接入。左值 awaiter 保留引用，右值 awaiter 按值保存。

恢复适配的核心是：

```cpp
decltype(auto) await_resume() {
  restore_task_context(*context);
  return inner.await_resume();
}
```

`await_ready()` 和 `await_suspend()` 原样转发，保留底层 `bool`、`void` 或协程句柄的挂起语义。恢复时先安装任务组与停止令牌，再领取底层结果。即使底层 `await_resume()` 抛异常，父任务的异常处理代码也已经处于正确的任务上下文中。

## 5. this_coro：任务内的查询与让出

### 5.1 标记函数与 await_transform 分发

[this_coro.hpp](../include/faio/detail/coroutine/this_coro.hpp) 定义一组无成员的标记类型和对应的 `inline constexpr` 函数。调用标记函数只创建一个空标记，不执行查询或调度；真正的行为发生在 `co_await` 该标记时，由 promise 的 `await_transform()` 重载解释为具体 awaiter：

| 标记 | await_transform 产物 | 行为 |
| --- | --- | --- |
| `stop_token_t` | `query_awaiter<std::stop_token>` | 立即取得 promise 保存的停止令牌 |
| `scheduler_t` | `query_awaiter<scheduler_ref>` | 立即取得任务的调度借用引用 |
| `worker_id_t` | `worker_id_awaiter` | 恢复时动态读取当前执行线程编号 |
| `priority_t` | `query_awaiter<task_priority>` | 立即读取任务优先级元数据 |
| `yield_t` | `yield_awaiter` | 将当前协程重新入队 |
| `yield_if_needed_t` | `yield_if_needed_awaiter` | 预算耗尽时将当前协程重新入队 |

查询读取的是 promise 内随帧保存的上下文，而不是此时线程上可能已经变化的 TLS。这条路径不启动调度，也不延长运行时生命周期。

### 5.2 属性查询 awaiter

`query_awaiter<T>` 在 `await_transform()` 中取得属性快照，`await_ready()` 恒为 `true`，`await_resume()` 直接返回快照。整个查询没有挂起和调度成本。

`worker_id_awaiter` 不保存任何成员，`await_resume()` 才读取线程局部的 worker 编号。任务挂起后可能迁移到其他 worker 恢复，挂起前保存的编号不能代表恢复后的执行位置，因此编号必须动态读取；未被运行时管理的线程返回 `no_worker_id` 哨兵。

### 5.3 协作让出 awaiter

`yield_awaiter` 按值保存恢复所需的全部上下文：调度借用引用、任务组指针和停止令牌指针，避免提交时再解引用 promise：

```cpp
bool await_ready() const noexcept { return false; }
void await_suspend(std::coroutine_handle<> h) const { scheduler.schedule(h); }
void await_resume() const noexcept {
  current_tracker = scope;
  current_stop_token = *stop_token;
}
```

`await_ready()` 恒为 `false`，让出总是经过一次重新入队；具体由哪个 worker、在何时恢复由调度器决定。

`yield_if_needed_awaiter` 借用 promise 内 `task_context` 的地址，`await_ready()` 递减预算：预算非零时立即完成，归零时进入与 `yield_awaiter` 相同的重新入队路径。`await_resume()` 只在实际让出后把预算重置为 64，立即完成路径保留递减结果；预算已为零时不再递减，避免无符号回绕成很大的预算。

预算按调用次数消耗而不是时间片，它是 CPU 密集循环主动让出执行机会的协作机制。重新入队的队列选择与恢复时机见[异步运行时](异步运行时.md)的协程调度章节。

## 6. 等待节点：统一的挂起设施

I/O 完成、定时器到期、同步原语通知和并发组合完成，最终都归结为"挂起一个协程，条件满足时把它投回调度域"。[coroutine_wait.hpp](../include/faio/detail/coroutine/coroutine_wait.hpp) 把这条路径收敛为两个设施：帧内等待节点 `wait_node` 和侵入式队列 `wait_queue`，并在其上实现一次性完成事件 `completion_event`。

### 6.1 wait_node 的成员与所有权

```cpp
struct wait_node {
  std::coroutine_handle<> handle{};
  scheduler_ref scheduler{};
  wait_node* next{};
  bool queued{};
  std::atomic<unsigned char> phase{0};
  struct cancel_callback { /* node、mutex、queue、has_waiters */ };
  std::optional<std::stop_callback<cancel_callback>> callback;
};
```

节点嵌入 awaiter，awaiter 保存在等待任务的协程帧中，因此节点地址在登记后保持稳定。等待队列只借用节点地址；通知或取消完成交接、协程恢复之后，才允许清理 awaiter。移动构造创建的是新的空节点，不迁移地址相关状态——已经登记的节点不能靠移动改变身份。

`capture()` 记录待恢复的协程句柄和登记线程的调度器，通知可以来自任意线程，恢复仍投回节点所属的调度域。`register_stop()` 为本次等待注册当前任务的停止令牌，必须在释放队列锁后调用：`std::stop_callback` 面对已停止的令牌会同步执行回调，持锁构造会造成同一把锁的重复获取。令牌不可取消时跳过回调构造，保留简单的等待路径。

### 6.2 wait_queue 的侵入式 FIFO

`wait_queue` 是不拥有节点的单链表，自身不带锁，所有操作由所属原语的互斥区保护。`push()` 尾插并标记 `queued`，`pop()` 摘除队首并把唯一通知权交给调用方，`take_all()` 摘除整条链供批量通知，`remove()` 按地址撤回节点。尾插和队首摘除为 O(1)，取消撤回为 O(n)，只在慢路径承担线性成本。

摘除节点的同时清除其 `queued` 标志，取消回调据此判断节点是否还能被撤回——通知与取消通过同一把队列锁争夺摘除权，一个节点只由一个路径接管。

### 6.3 登记与通知的交接

原子 `phase` 协调"登记尚未完成"与"通知已经到达"的竞态：

| 值 | 含义 |
| --- | --- |
| 0 | 登记中，句柄和队列关系正在建立 |
| 1 | 已交给异步恢复路径，通知或取消需要调度入队 |
| 2 | 正常通知已到达 |
| 3 | 取消已到达 |

`arm()` 尝试把 phase 从 0 推进到 1，其返回值直接作为 `await_suspend()` 的返回：成功则协程真正挂起，失败说明通知或取消先于挂起到达，当前执行流直接继续。`wake()` 和 `cancel()` 分别把 phase 交换为 2 和 3，只有看到旧值 1 时才把句柄投回调度器。两条路径都只安排一次恢复。

`wake_all()` 和 `cancel_all()` 消费已摘除的节点链：唤醒一个节点前先保存其后继地址，因为入队成功后协程可能立即在其他 worker 恢复并销毁节点。登记、通知与取消的完整竞态分析见[协程同步](协程同步.md)的等待节点协议章节。

### 6.4 completion_event：一次性完成事件

`completion_event` 在 `wait_node` 之上实现带记忆的一次性事件，供结果句柄和并发组合使用。内部原子指针的三种含义：

| 指针状态 | 含义 |
| --- | --- |
| `nullptr` | 未完成且没有等待者 |
| 等待节点链表 | 未完成，已有协程登记 |
| `&completed_` | 永久完成标记 |

等待者以 CAS 将帧内节点头插到链表，再执行 `arm()` 完成交接。`notify()` 一次交换同时发布完成、摘除整条链并关闭后续登记，随后反转链表按登记顺序批量唤醒；重复通知保持幂等。完成事件不注册取消回调，借用其状态的任务组负责等待孩子退出。它在结果发布中的角色见[协程并发](协程并发.md)。

## 7. 调度边界：scheduler_ref 与执行线程绑定

协程层不实现队列和线程，只定义与运行时交互的协议。[scheduler.hpp](../include/faio/detail/coroutine/scheduler.hpp) 和 [execution_thread.hpp](../include/faio/detail/coroutine/execution_thread.hpp) 是这条边界的两侧：前者是任务持有的调度入口，后者是执行线程向外提供的能力。

### 7.1 类型擦除的调度借用引用

`coroutine_scheduler` 概念要求具体调度器提供 `enqueue(handle) -> void`，语义约束是：成功接受句柄后安排一次恢复，不在 `enqueue` 内直接 `resume()`；抛异常表示没有接管句柄，提交方据此安全回滚。`ready_sink` 概念约束所属线程的就绪接收端，I/O 和定时器报告完成时无需知道具体队列布局。

`scheduler_ref` 是两个指针的类型擦除引用：一个借用具体调度器实例，一个借用按该类型生成的静态操作表。操作表把擦除后的指针转换回真实类型再调用 `enqueue()`：

```cpp
void schedule(std::coroutine_handle<> handle) const {
  if (!*this) throw std::logic_error("没有可用的调度器");
  ops_->enqueue(state_, handle);
}
```

该引用不分配内存、不持有所有权，也不管理根任务计数；具体调度器必须存活到使用它的协程与等待节点全部结束。相等比较同时比较实例与操作表，用于判断本地快路径是否属于同一个调度域。

### 7.2 执行线程绑定

worker 进入事件循环前，在同一次构造中绑定四类能力并安装线程局部指针：

- 当前调度域的 `scheduler_ref`；
- 运行时根任务计数的 `task_lifetime_ref`；
- 本地就绪状态地址及其类型标识；
- 当前 worker 编号，无编号时使用 `no_worker_id` 哨兵。

`local_state_for<T>()` 同时校验调度域身份和类型标识，只有匹配本调度域、本地队列类型的线程才能取回本地状态，避免对任意后端盲目转换。类型标识使用每类型唯一的静态变量地址，不依赖 RTTI。

`execution_thread_guard` 构造时安装线程局部绑定、析构时恢复原值，成对使用保证嵌套安装后不留悬空指针。协程层通过四个查询函数读取能力：

| 查询 | 语义 |
| --- | --- |
| `current_scheduler()` | 当前线程的调度入口；普通线程返回空引用 |
| `current_task_lifetime()` | 根任务生命周期服务，供 worker 内派生任务继承 |
| `current_worker_id()` | 动态读取线程编号，任务迁移后需重新查询 |
| `on_runtime_worker()` | 判断是否为已绑定的执行线程，阻塞入口据此拒绝调用 |

任务上下文的 `scheduler` 表示调度域归属，worker 编号表示当前执行位置：任务经队列和窃取恢复后调度域保持不变，编号随实际执行线程变化。绑定的安装时机、入队路径选择和事件循环行为见[异步运行时](异步运行时.md)。
